# Лабораторная работа №4

## «Морской бой» — многопользовательская веб-игра в режиме реального времени

Подробное описание требований: теория и реализация.

---

## 1. Постановка задачи

Разработать многопользовательскую веб-игру в режиме реального времени. В качестве игры реализован классический «Морской бой» для двух игроков.

**Обязательные требования:**

1. Мгновенная синхронизация действий игроков у всех участников через WebSockets.
2. Использование только JavaScript, без фреймворков.
3. Сохранение данных игры между запусками приложения.

**Дополнительные требования (оценка 8–10):**

1. Учёт конкурентного доступа и разрешение конфликтов при одновременном редактировании одного элемента.
2. Сохранение состояния и восстановление после потери интернет-соединения.
3. Развёртывание готового приложения на хостинге и предоставление ссылки.

---

## 2. Архитектура приложения

Приложение построено по схеме «клиент — авторитетный сервер». Вся игровая логика и состояние находятся на сервере; браузер только отображает состояние и отправляет действия. Обмен данными — JSON-сообщения поверх WebSocket.

```
Laba4/
├── server.js           — HTTP-сервер + WebSocket (RFC 6455) + логика игры + авторизация + сохранение
├── public/
│   ├── index.html      — разметка (панель входа, таблица результатов, два игровых поля)
│   ├── style.css       — оформление
│   └── game.js         — клиентская логика (vanilla JS)
├── package.json        — манифест для хостинга (start: node server.js)
├── games.json          — состояние партий (создаётся автоматически)
└── users.json          — пользователи и их результаты (создаётся автоматически)
```

Протокол (клиент → сервер): `join`, `shoot`, `restart`, `register`, `login`, `restore`, `logout`, `results`.
Сервер отвечает: `joined`, `waiting`, `state`, `event`, `error`, `auth`, `results`.

## 3. Требование 1 — синхронизация действий через WebSockets

### 3.1. Теория

WebSocket — протокол поверх TCP (RFC 6455), дающий постоянное двунаправленное соединение между браузером и сервером. Обычный HTTP работает по схеме «запрос → ответ»: клиент открывает соединение, получает ответ, соединение закрывается. Для реального времени это неудобно — пришлось бы постоянно опрашивать сервер (polling) либо держать зависший запрос (long-polling). WebSocket решает проблему иначе: соединение устанавливается один раз через HTTP-апгрейд, после чего обе стороны обмениваются кадрами без повторных запросов. Это даёт минимальную задержку и позволяет серверу «проталкивать» данные клиенту мгновенно.

**Рукопожатие.** Клиент шлёт обычный GET с заголовками `Upgrade: websocket` и `Sec-WebSocket-Key`. Сервер подтверждает ответом «101 Switching Protocols» с ключом `Sec-WebSocket-Accept`, который вычисляется как SHA-1 от конкатенации `Sec-WebSocket-Key` и фиксированной строки `258EAFA5-E914-47DA-95CA-C5AB0DC85B11`.

**Кадр WebSocket.** Первый байт содержит FIN и opcode (тип кадра: 1 — текст, 8 — закрытие, 9 — ping, 10 — pong), второй — бит маски и длину (7, 16 или 64 бита). Кадры от клиента к серверу обязательно маскируются 4-байтовым ключом, сервер шлёт кадры без маски.

### 3.2. Реализация

Рукопожатие на сервере (обработчик события `upgrade`):

```js
server.on('upgrade', (req, socket, head) => {
  const accept = crypto.createHash('sha1')
    .update(req.headers['sec-websocket-key'] + WS_MAGIC)
    .digest('base64');
  socket.write('HTTP/1.1 101 Switching Protocols\r\n' +
    'Upgrade: websocket\r\n' +
    'Connection: Upgrade\r\n' +
    'Sec-WebSocket-Accept: ' + accept + '\r\n\r\n');
  const ws = new WS(socket);
  ws.onmessage = (text) => handleMessage(ws, text);
  ws.onclose = () => handleDisconnect(ws);
  if (head && head.length) ws._onData(head); // не теряем байты первого кадра
});
```

Разбор кадров реализован вручную в классе `WS`:

```js
const opcode = b0 & 0x0f;            // тип кадра
const masked = (b1 & 0x80) !== 0;    // клиент обязан маскировать
let len = b1 & 0x7f;                 // длина полезной нагрузки
// ... чтение расширенной длины (126/127) и ключа маски ...

if (opcode === 0x1) {                // текстовый кадр
  this.onmessage(payload.toString('utf8'));
} else if (opcode === 0x8) {         // close
  this._closed();
} else if (opcode === 0x9) {         // ping -> pong
  this._sendFrame(payload, 0xA);
}
```

Рассылка события всем участникам — именно это обеспечивает синхронизацию:

```js
function sendToGame(game, obj) {
  for (const p of game.players) if (p.ws) p.ws.send(JSON.stringify(obj));
}

// onShoot: результат выстрела уходит обоим
sendToPlayer(game, idx,     { type: 'event', text: evShooter });
sendToPlayer(game, 1 - idx, { type: 'event', text: evOpp });
sendAllState(game);   // полное состояние поля и очереди хода
```

На клиенте:

```js
const proto = location.protocol === 'https:' ? 'wss' : 'ws';
ws = new WebSocket(`${proto}://${location.host}`);
ws.onopen    = () => send({ type: 'join', name, token, authToken });
ws.onmessage = (e) => handle(JSON.parse(e.data));

function send(obj) {
  if (ws && ws.readyState === WebSocket.OPEN) ws.send(JSON.stringify(obj));
}
```

## 4. Требование 2 — только JavaScript, без фреймворков

### 4.1. Теория

Фреймворк — это каркас, навязывающий структуру приложения (Express, Socket.IO, React, Vue и т.п.). Требование означает, что решение обходится средствами самого языка и платформы: на сервере это Node.js со встроенными модулями, в браузере — нативный JavaScript и DOM API. В данной работе нет даже сторонних библиотек: WebSocket написан вручную, чтобы полностью соответствовать требованию.

### 4.2. Реализация

```js
// server.js — только встроенные модули Node.js, npm-зависимостей нет
const http   = require('http');   // HTTP-сервер и upgrade-запросы
const crypto = require('crypto'); // SHA-1 (рукопожатие) и scrypt (пароли)
const fs     = require('fs');     // чтение/запись состояния на диск
const path   = require('path');   // пути к статике
```

Клиент использует только стандартный объект `WebSocket`, `document.createElement` для построения полей и `addEventListener` для обработки кликов — без библиотек и сборщиков.

## 5. Требование 3 — сохранение данных между запусками

### 5.1. Теория

Состояние приложения по умолчанию живёт только в оперативной памяти процесса и теряется при остановке. Для сохранения между запусками его сериализуют во внешнее хранилище. Здесь выбран JSON-файл: он нативно читается и пишется (`JSON.stringify` / `JSON.parse`), человекочитаем и не требует СУБД. Запись выполняется синхронно (`fs.writeFileSync`) после каждой значимой операции — операции редкие, а объём данных мал.

### 5.2. Игровое состояние — games.json

```js
function saveState() {
  const savable = {};
  for (const [id, g] of Object.entries(state.games)) {
    savable[id] = { id: g.id, status: g.status, turn: g.turn, winner: g.winner,
      players: g.players.map((p) => ({ id: p.id, token: p.token, name: p.name,
        grid: p.grid, ships: p.ships, shots: p.shots })) };
  }
  fs.writeFileSync(SAVE_FILE, JSON.stringify({ games: savable }, null, 2));
}

function loadState() {
  const data = JSON.parse(fs.readFileSync(SAVE_FILE, 'utf8'));
  // ... state.games заполняется из файла, у игроков сбрасывается ws = null
}
```

`saveState()` вызывается при подключении игрока, после каждого выстрела, при перезапуске партии и при отключении игрока. При старте вызывается `loadState()`.

### 5.3. Пользователи и результаты — users.json

Расширение требования: пользователи авторизуются, чтобы видеть таблицу своих результатов. Пароль не хранится в открытом виде — используется scrypt с солью:

```js
function hashPassword(password, salt) {
  return crypto.scryptSync(String(password), salt, 64).toString('hex');
}

function onRegister(ws, msg) {
  const username = String(msg.username || '').trim();
  const password = String(msg.password || '');
  if (!/^[a-zA-Zа-яА-Я0-9_-]{3,20}$/.test(username)) { /* неверный формат */ }
  if (password.length < 4) { /* слишком короткий */ }
  if (users[username]) {       // проверка уникальности логина
    ws.send(JSON.stringify({ type: 'auth', ok: false, error: 'Такой логин уже занят.' }));
    return;
  }
  const salt = crypto.randomBytes(16).toString('hex');
  users[username] = { salt, hash: hashPassword(password, salt), results: [] };
  saveUsers();                 // запись на диск
}
```

После завершения партии результат записывается в таблицу обоих игроков:

```js
function recordResult(game) {
  if (game.winner === null) return;
  for (let i = 0; i < game.players.length; i++) {
    const p = game.players[i];
    if (!p.authUsername) continue; // гость — результат не сохраняем
    users[p.authUsername].results.push({
      opponent: game.players[1 - i].name,
      result: i === game.winner ? 'win' : 'loss',
      date: Date.now(),
    });
  }
  saveUsers();
}
```

## 6. Доп. 1 — конкурентный доступ и разрешение конфликтов

### 6.1. Теория

Когда несколько пользователей одновременно пытаются изменить один элемент (в «Морском бое» — выстрелить в одну и ту же клетку или сходить вне очереди), возникает гонка данных. Решение — модель авторитетного сервера: вся логика и состояние находятся на сервере, клиенты лишь присылают намерения. Дополнительно Node.js обрабатывает сообщения в одном потоке (event loop), поэтому внутри процесса гонок нет — сообщения обрабатываются строго последовательно. Конфликт разрешается правилом «побеждает первая корректная операция»: повторные действия по уже изменённому элементу отклоняются.

### 6.2. Реализация

```js
// onShoot: сервер валидирует каждый выстрел перед применением
if (game.turn !== idx) {
  // ходит другой игрок — действие отклоняется
  ws.send(JSON.stringify({ type: 'error', message: 'Сейчас ход противника.' }));
  return;
}
if (opp.shots[y][x] !== null) {
  // в клетку уже стреляли (повторное редактирование одного элемента)
  ws.send(JSON.stringify({ type: 'error', message: 'В эту клетку уже стреляли.' }));
  return;
}
// ... только после всех проверок состояние меняется и рассылается
```

## 7. Доп. 2 — восстановление после потери соединения

### 7.1. Теория

Чтобы пережить обрыв сети, игрок должен быть идентифицируем после переподключения. Для этого каждому игроку выдаётся уникальный токен. Клиент сохраняет токен и при обрыве автоматически переподключается, отправляя его же; сервер по токену находит игрока и восстанавливает партию. Игровой токен хранится в `sessionStorage` — он свой у каждой вкладки (иначе две вкладки с одним токеном боролись бы за одного игрока), но переживает обновление страницы.

### 7.2. Реализация

```js
// клиент: авто-переподключение
let token = sessionStorage.getItem('bs_token') || null;

ws.onclose = () => {
  setConnStatus('Соединение потеряно. Переподключение…');
  reconnectTimer = setTimeout(connect, 2000);
};

// сервер: восстановление игрока по токену
function onJoin(ws, msg) {
  if (msg.token) {
    const ref = findPlayerByToken(msg.token);
    if (ref) {
      ref.game.players[ref.idx].ws = ws;        // новый сокет
      ref.game.players[ref.idx].connected = true;
      sendAllState(ref.game);                    // актуальное состояние
      return;
    }
  }
  // ... иначе создаём нового игрока
}
```

Аналогично восстанавливается сессия авторизации по `authToken` (сообщение `restore`).

## 8. Доп. 3 — развёртывание на хостинге

### 8.1. Теория

Платформы типа Render / Railway / Fly.io запускают приложение как обычный Node.js-процесс и проксируют на него трафик. Порт передаётся через переменную окружения `PORT`, а TLS (HTTPS/wss) завершает сама платформа. Поэтому приложение должно читать порт из окружения и корректно выбирать протокол на клиенте.

### 8.2. Реализация

```js
// server.js — порт из окружения
const PORT = process.env.PORT || 3000;

// game.js — автоматический выбор протокола
const proto = location.protocol === 'https:' ? 'wss' : 'ws';
ws = new WebSocket(`${proto}://${location.host}`);
```

Команды запуска в `package.json`:

```json
{
  "scripts": { "start": "node server.js" },
  "engines": { "node": ">=18" }
}
```

На Render: **Build Command** — `npm install`, **Start Command** — `npm start`. После деплоя сервис доступен по ссылке вида `https://<имя>.onrender.com`, WebSocket работает на том же хосте по `wss`.

## 9. Дополнительно: логика «Морского боя»

### 9.1. Расстановка кораблей (корабли не касаются)

По правилам корабли не должны касаться друг друга даже углами. При случайной расстановке проверяется, что сама клетка и все 8 её соседей свободны:

```js
const cellFree = (x, y) => {
  for (let dy = -1; dy <= 1; dy++) {
    for (let dx = -1; dx <= 1; dx++) {
      const nx = x + dx, ny = y + dy;
      if (nx >= 0 && nx < SIZE && ny >= 0 && ny < SIZE && grid[ny][nx] !== null)
        return false;
    }
  }
  return true;
};
// корабль ставится, только если все его клетки cellFree
if (cells.every(([cx, cy]) => cellFree(cx, cy))) { /* разместить */ }
```

### 9.2. Потопление корабля и «ореол»

Корабль потоплен, когда `hits == size`. В представлении игрока его клетки помечаются как `sunk`, а клетки вокруг — как `halo` (там не может быть другого корабля, по ним стрелять не нужно):

```js
const sunkOpp = new Set(opp.ships.filter(s => s.hits >= s.size).map(s => s.id));
// клетка попадания, принадлежащая потопленному кораблю -> 'sunk'
// соседи потопленного корабля, по которым ещё не стреляли  -> 'halo'
if (oppShot === 'hit' && sunkOpp.has(oppShipId)) shot = 'sunk';
else if (oppShot === null && haloOpp.has(y * SIZE + x)) shot = 'halo';
```
